# Где ускорять ArtLapse: измерения этапа204

Проверка 22.10.2026 по запросу владельца. Исследована версия `b42f1dc`
(ArtLapse203). Это аудит с отдельными экспериментами: исходники приложения
и рабочая сборка не изменялись, новый EXE не собирался.

## Условия

Локальный фрагмент реальной записи:120секунд начиная с3600секунды,
2560×1440,30FPS. Создан отдельный MP4 для измерений; оригинальная запись
не переписывалась, её fingerprint до/после совпал.24логических CPU,
OpenCV4потока, собственный FFmpeg8.1.2-ArtLapse-202, NVENC доступен.
План Shorts на6секунд,12рендер-фрагментов,127сегментов анализа.

Основной проход измерен с cProfile, поэтому содержит его накладные расходы.
Сравнительные эксперименты выполнялись последовательно без профилировщика.
Это один фрагмент, без разметки качества скульптинга; результат нельзя
переносить в виде обещанного коэффициента на многочасовые записи.

## Приоритет1: совместимые рендер-фрагменты и повторные проверки

Контроль: один и тот же непрерывный120-секундный материал ускорен до6секунд
в режиме speed.20совместимых последовательных решений по9кадров против
одного решения на180кадров:

| Схема | Время, с |
|---|---:|
|20фрагментов|21,412|
|1фрагмент|6,939|

Оба варианта здесь замерены без профилировщика (render_compare.json).
Это иллюстрация цены дробления, а не готовое ускорение обычного Shorts в3раза.
Оба файла:180кадров,6секунд,30FPS,2560×1440, ffprobe и полное декодирование PASS.
Покадровое сравнение PSNR56,33dB; файлы не побитово идентичны из-за кодирования.

В исходном профилированном запуске20фрагментов занимали21,493с,
89процессов.21вызов `verify_output` занимает6,865с
(около32%экспорта), из них21отдельный metadata-probe1,093с. Создание
процессов само по себе0,323с: всё время ожидания процессов считать
«накладными расходами запуска» неправильно, там также декодирование/кодирование.

Следующее изменение: объединять соседние участки только при совместимых
источнике, времени, темпе, кадрировании, камере, действии и границах HOLD/
презентации/финала. Отдельно объединить получение metadata и count_frames
в один ffprobe. Сохранить проверку таймингов, числа кадров, аудио, decode,
отмену и возможность безопасного возобновления. Простое удаление проверок
по этому измерению не обосновано.

## Приоритет2: точные визуальные расчёты и ограниченное повторное использование

Экспериментальная замена `np.median` для uint8-изображения на точную медиану
256-бинной гистограммы, без изменения порогов:

- 615проверок медианы совпали точно (реальные и граничные/случайные кадры).
- 1800проверок `screen_kind` на600кадрах: все ответы совпали.
- Три пары суммарного времени проверки600кадров:2,397→1,939с;
 2,186→1,746с;2,167→1,703с. Медиана времени уменьшилась примерно на20%.
- Полное перестроение плана, порядок baseline/prototype/prototype/baseline:
 17,460/16,774/16,593/17,030с. По медианам17,245→16,684с, на3,26%меньше.
 Полные JSON-планы совпали по SHA256 во всех четырёх запусках.

Отдельный прототип с ограниченным кэшем256результатов `screen_kind`
использует форму/dtype/настройки/хеш точных входных пикселей. Полные кадры
не хранит.196повторных обращений из925, на хеши0,33–0,34с. Два контрольных
и два экспериментальных прогона: медианы16,813→16,223с (около3,5%).
Разброс контроля16,115–17,511с больше эффекта, поэтому оценка предварительная.
Все четыре полных плана совпали с прежним SHA256:
`737fb584051389dba4c3408ed880e3cfc82552aa80e156ff8431bb1f1fd672b1`.
Проценты двух прототипов нельзя складывать: они затрагивают одни проверки.

Следующее изменение: сначала точный uint8-путь с тестами чётного/нечётного
числа пикселей, затем ограниченный кэш нужных визуальных результатов.
Ключи должны учитывать реальные пиксели/режим/ROI/webcam/версию; состояние
сопровождения модели нельзя безусловно кэшировать только по времени кадра.

## Остальные кандидаты

- Признаки и движение: уменьшать повторные преобразования/медианы/выделения
 памяти по профилю. Общий декодер — вторым шагом. Сохранить checkpoint,
 отмену, ограниченную память и детерминированность.
- Классификация и SQLite: N+1-запросы существуют, но на этом фрагменте
 классификация0,03с, оценка важности0,23с. Они не первый приоритет;
 полезность потокового соединения нужно проверить на длинном источнике.
- Повторная проверка FFmpeg/NVENC `doctor`: медиана0,320с,4процесса на вызов.
 Кэш на одну задачу может убрать небольшую задержку, сохранив CPU fallback.
- Текущий кэш плана работает:0,009с. Уменьшение FPS/разрешения анализа и
 изменение порогов ради скорости в этом аудите не проверялись.
